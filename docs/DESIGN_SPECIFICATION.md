# 1. システム概要

本システムは  
**個人用シフト・給与概算管理Webアプリ**である。

主な機能

- シフト登録・編集・削除
- 月間カレンダー表示
- 概算給与計算・集計
- Google Calendar同期

# 2. システム構成

**アーキテクチャレイヤー**

| レイヤー           | 技術スタック           | 説明                                     |
| ------------------ | ---------------------- | ---------------------------------------- |
| **フロントエンド** | Browser + React 19     | ユーザーブラウザで実行される UI レイヤー |

- NextAuth.js を使用した Google OAuth 認証
- 単一ユーザー対応

**通信フロー**

Browser (React UI) → Next.js Routes → Prisma ORM → Neon DB

外部連携: Neon ← → Google Calendar API

## 2.2 データ取得・キャッシュ戦略（2026-07 更新）

2026-05 のパフォーマンス改善で、読み取りキャッシュ責務を **Server Cache（Next.js Cache Components）** と **Client Cache（TanStack Query）** に整理した。

### サーバー側（Route Handler / Server Components）

- API レスポンスは `lib/api/cache-control.ts` を経由し、機密データを含むレスポンスを `private, no-store` 中心で返却する。
- `POST /api/shifts/bulk` は認証済みユーザー単位で60秒あたり5回までとする。CSRF 検証に失敗したリクエストは枠を消費しない。超過時は JSON エラーと `429`、`Retry-After`（残り秒数）、`private, no-store` を返す。制限は各 Node.js instance のメモリに保持する best effort 制御であり、instance 間では共有しない。期限切れのユーザー記録は expiry FIFO でアクセス時に削除し、記録数は最大10,000件に制限する。上限時は最も早く期限切れになる記録を破棄する。
- `parseJsonBody` を利用するすべての更新リクエスト（Route Handler と Server Action）は、JSON 本文を 1 MiB（UTF-8 バイト数）までに制限する。上限を超える有効な `Content-Length` は本文読取前に、ヘッダー未指定・不正・chunked の本文はストリーム読取中に拒否し、いずれも `413` と `{ "error": "リクエスト本文が大きすぎます" }` を `private, no-store` で返す。JSON 構文・UTF-8・スキーマの既存エラー契約（400）は維持する。
- `/my`・`/my/shifts/list` の初期月次シフト取得は `lib/shifts/month-shifts.ts` の共通 DAL で取得し、初回表示時の重複 fetch を避ける。
- 勤務先・給与ルール・時間割の参照系は、ユーザーと関連 ID をキーにした serializable DTO を Server Cache（`cacheLife("max")` + tags）へ保存する。GET API は `private, no-store` のまま、このキャッシュ済み DAL を呼び出す。
- 勤務先・給与ルール・時間割の作成/更新/削除は公開 Mutation REST Route を持たず、共通認証・既存 Zod 検証・所有確認を行う Server Action 経由で実行する。DB 更新後は `updateTag` で勤務先および給与関連タグを即時無効化する。
- Mutation 後のクライアント整合性は、既存の React Query ドメイン単位 invalidation と Undo / Google Calendar 同期契約を維持する。Route core の `revalidateTag` は更新経路では使用しない。

### クライアント側（React Query）

- App 全体を `QueryClientProvider` で包み、クライアント再表示時の読み取り状態を query cache で統一する。
- query key は `lib/query/query-keys.ts` で一元管理し、`shifts` / `payroll` / `workplaces` ドメインで衝突しないキー体系を維持する。
- `payroll` ドメインには `summary` / `details` / `previewBaseline` に加え `actual`（実給与編集）を含め、実給与更新後は給与サマリー・給与詳細・実給与編集を同時に再取得する。
- fetch は `lib/query/fetch-json.ts` で共通化し、エラー種別の正規化と UI メッセージ解決を統一する。
- 月次シフト・給与集計/詳細・勤務先管理一覧・シフト確定・各フォーム編集時の読み取りは TanStack Query を利用する。
- 単体シフト入力と一括入力の勤務先初期データは `/api/shifts/form-bootstrap` で一括取得し、勤務先一覧 + 選択勤務先詳細 + 給与ルール + 時間割セットをまとめて扱う。
- 月/年切替や再取得では `placeholderData` により直前データを維持し、既存の LoadingOverlay・`aria-busy=true`・操作制御を維持する。再取得中の画面内インライン通知は、対象画面すべてで右下の非操作型スピナーと `更新中` をフローティング表示する方式へ統一する。
- 初回表示時の full spinner / skeleton と、保存中の表示・操作制御は再取得時とは別の仕様として維持する。
- Mutation 後の整合は `lib/query/invalidation.ts` のドメイン単位 invalidation で行い、手動 reload を原則廃止する。
- 削除操作（単体シフト、選択シフト一括、勤務先、給与ルール、時間割セット）は確認ウィンドウを表示しない。削除クリック直後に対象を楽観的に表示から除去し、「削除しました」などの完了表現と4秒間の「元に戻す」アクションを持つトーストを表示する。
- 上記トーストの期限内に「元に戻す」を選択した場合は削除 Server Action を呼ばず、除去した表示を復元する。期限経過後は削除 Server Action による hard delete をバックグラウンドで実行し、成功時に追加トーストは表示しない。失敗時は表示を復元してエラー通知する。
- シフト削除導線は月次 `shifts.month` キャッシュを楽観的に更新し、削除時には進行中の月次取得をキャンセルする。削除処理後は月次キャッシュを即時再フェッチせず、一覧・カレンダーから除去した行が古い取得結果で再表示されないことを優先する。
- 日跨ぎ終了のシフト保存・確定で表示する内容確認ダイアログは削除操作とは別の仕様であり、引き続き表示する。
- 単体シフトの登録・編集は保存成功レスポンスの `data` を使って `shifts.month` キャッシュへ即時反映し、遷移は再取得完了待ちでブロックしない。
- 一括登録も保存成功レスポンスの `data[]` を使って `shifts.month` キャッシュへ即時反映し、複数件登録後も `/my` 遷移を重い invalidation で待たせない。
- `/my` は未確定件数を SSR 初期データとして表示し、画面を開くたびクライアントで件数をバックグラウンド再取得する。再取得中は右下の非操作型「更新中」フローティング表示を出し、画面全体をブロックしない。
- シフト確定ページは SSR の未確定シフト一覧を初期表示する。画面を開くたびクライアントで未確定一覧の有無・内容をバックグラウンド再取得し、右下の非操作型「更新中」フローティング表示を出す。確定成功後は対象カードを即時除去し、関連キャッシュは stale 化する。利用者の手動「更新」操作も引き続き利用でき、いずれの再取得も画面全体をブロックしない。
- シフト更新後の再取得は `shifts` を優先し、給与集計・勤務先関連の invalidation は導線に応じてバックグラウンド化を許容する。
- シフト系の更新APIは `sync` オブジェクト（`status`/`pending`/`requiresCalendarSetup`/`requiresSignOut` など）を返し、DB更新成功と外部同期状態を分離して扱う。
- 勤務先/給与ルール/時間割/ユーザー更新APIも `sync` を返し、外部同期がない操作では `status=success` として扱う。
- クライアントは保存成功後の遷移を同期完了待ちでブロックせず、`sync.pending=true` の場合は「Google Calendar 同期はバックグラウンドで実行中」と明示する。
- Google Calendar 初期化後の既存シフト同期も同様にバックグラウンド実行とし、初期化画面の遷移を待たせない。
- 旧 `lib/client-cache/*` は廃止し、二重キャッシュを解消する。

### 初期表示と hydration

- Server Component で取得した初期データは `initialData` として query に注入する。
- `useMonthShifts` は `staleTime` を設定し、hydration 直後の即時 refetch によるローディング退行を抑制する。
- Google Calendar 予定参照 API（`/api/calendar/events`）は専用の短期メモリキャッシュを持ち、期限切れ時は stale fallback と警告表示を許容する（書き込み同期の正は DB）。

## 2.3 認証導線と初期表示最適化（2026-07 更新）

2026-07 の初期表示改善では、`/my` 配下の認証境界を維持したまま、共通レイアウトの待機と不要な自動 prefetch を削減した。

### 認証の正本

- `/my` 系の認証保護は `proxy.ts` ではなく、Server Component の page/layout と Route Handler 側で行う。
- `/login` は server-side で `auth()` を評価し、認証済みなら `/my` へ即時 redirect する。
- `requireCurrentUser()` / `requireSessionAndCurrentUser()` を認証済みユーザー解決の共通入口とし、page/layout/API ごとに独自 lookup を増やさない。

### current user 解決方針

- `auth()` の session には `id`、`email`、`calendarId`、`googleTokenExpiresAt`、`createdAt`、`updatedAt` を含め、`requireCurrentUser()` はまず session.user から current user を復元する。
- DB lookup は、session に必要項目が欠ける場合の fallback に限定する。
- fallback lookup を使う場合も request-scope cache で再利用し、同一リクエスト内の重複照会を避ける。

### `/my` シェルの責務

- `app/my/layout.tsx` はシェル描画を担当し、認証待機を持たない。
- 未認証 redirect と `calendarId` 未設定時の `/my/calendar-setup` 誘導は、`app/my/(requires-calendar)/layout.tsx` と各 page 側で行う。
- サイドバーのユーザー表示は `/api/users/me` を client fetch し、シェル初期描画を user hydrate 待ちでブロックしない。

### 画面初期表示の待ち時間削減

- `/my` は `getMonthShifts`、`getUnconfirmedShiftCount`、`getPayrollSummaryAmountForUser` を server-side で並列取得し、翌月支給額も SSR 初期データとして注入する。未確定件数は画面表示後にもクライアントで背景再取得し、右下の「更新中」フローティング表示で通知する。
- `/my/shifts/confirm` は SSR の未確定一覧を初期表示したうえで、画面を開くたび未確定一覧の有無・内容をクライアントで背景再取得する。再取得は非ブロッキングで、右下の「更新中」フローティング表示と手動「更新」操作を維持する。
- `getMonthShifts` と `getUnconfirmedShiftCount` は user 単位の Server Cache を使い、初回表示と関連画面で再利用する。
- `/my/summary` は初期表示時点で `getPayrollSummaryForUser` の 1 回だけを正本とし、月次集計と年内 context の二重初期取得を行わない。

### ナビゲーションと blocking-route 回帰防止

- サイドバーの link は `prefetch={false}` を基本とし、hover/focus 時のみ意図的 prefetch を行う。
- pathname 依存 UI（パンくず、アクティブ表示など）は Suspense 配下の client component に分離し、共通 layout 全体を blocking-route 化しない。
- Route Handler で計測のために `connection()` を扱う場合は、`measure(() => connection())` で包まず、直接 `await connection()` を `startStep/endStep` で囲む。

### 月表示の URL 状態

- `/my`、`/my/shifts/list`、`/my/shifts/bulk` の表示月は `month=YYYY-MM` query param を正本とする。未指定または不正値の場合は現在月を表示する。
- 月移動は `router.replace` で同 query param を更新し、履歴を増やさない。ダッシュボードからの一括登録、および一括登録完了・キャンセル後のダッシュボード復帰では表示月を引き継ぐ。

### 計測方針

- `SHIFTA_PERF=1` 時は `request-timing` と `auth-timing` を有効化し、サーバーログと `Server-Timing` ヘッダーの両方に同一ラベルで出力する。
- auth 計測は少なくとも `auth`、`sessionResolve`、`sessionResolve:dbRead`、`sessionResolve:assemble`、`userHydrate` を比較可能に保つ。
- `/my`、`/my/summary`、`/api/payroll/summary*`、`/api/workplaces*`、`/api/shifts/form-bootstrap` は、回帰時に同じ計測ラベルで再比較できることを優先する。

## 3.1 User

**制約条件**

## 3.2 Workplace

勤務先（複数登録可能）

**説明**: ユーザーが勤務する企業・塾など。シフトの根拠となる組織。

| 属性      | 型       | 説明                                       |
| --------- | -------- | ------------------------------------------ |
| id        | UUID     | 勤務先の一意識別子                         |
| name      | string   | 勤務先名（例：「コンビニA」「塾B」）       |
| color     | string   | UIに表示する色（HEX形式）                  |
| type      | enum     | 勤務先の種別（GENERAL または CRAM_SCHOOL） |
| createdAt | datetime | 勤務先登録日時                             |

**制約条件**

- name は空でない
- color は HEX カラーコード（#RRGGBB）形式
- 1ユーザーあたり複数勤務先可能
- 削除時は、transaction 内で `Shift`、`PayrollRule`、`TimetableSet`、`ActualPayroll` の4項目の件数を取得し、返却する `relatedCounts` に含める。`ShiftLessonRange` と `Timetable` を含む関連データは CASCADE で削除し、Google Calendar イベント識別子も捕捉する。いずれかの DB 処理に失敗した場合は transaction を rollback し、勤務先と関連データを削除前の状態に戻す。削除競合時は `WORKPLACE_DELETE_CONFLICT` と HTTP 409 を返す。
- DB commit 後、捕捉した Google Calendar イベントは、bulk同期と共有する instance-local semaphore（最大3並列、待機列最大100）を通じて `after()` で best-effort 削除する。削除対象イベントがある場合は同期状態を `pending` として返す。外部削除に失敗しても DB 削除は戻さず、安全な件数要約ログのみを記録し、永続的な自動 retry/job は行わない。single-user MVPでは、稀な競合、Google Calendar 障害、`after()` 実行消失などによりイベントが残る可能性を受容する。
- Calendar イベント作成後に DB の成功更新件数が 0 件となった場合は、単体・一括とも所有確認付きの補償削除を best-effort で実行し、orphan イベントを抑制する。補償削除も永続 retry は行わない。

**使用例**

- name: "コンビニA"、type: GENERAL、color: "#FF5733"
- name: "英語塾"、type: CRAM_SCHOOL、color: "#3366FF"

**type の説明**

- **GENERAL**: 通常の勤務先（コンビニ、飲食店など）
- **CRAM_SCHOOL**: 塾（Timetable と ShiftLessonRange を使用）

## 3.3 PayrollRule

給与ルール履歴（勤務先ごとの時給管理）

**説明**: 勤務先ごとの時給・割増ルールを時系列管理。同一勤務先で複数ルールが存在し、シフト日に該当する有効なルールを自動選択する。

**ルール選択ロジック**: UI の適用開始日から適用終了日（この日まで）までを有効期間とする。内部では適用終了日の翌日を排他境界として保持し、`startDate ≤ shift.date < endDate` を満たすルール中、`startDate` が最新（最大）のものを選択する。該当期間のルールが複数保存されている場合も、`startDate` 降順で最初に見つかった 1 件を採用する。作成・更新時に重複候補がある場合、API は保存を継続したうえで warning を返す。

| 属性                   | 型     | 説明                                                                                            |
| ---------------------- | ------ | ----------------------------------------------------------------------------------------------- |
| id                     | UUID   | ルールの一意識別子                                                                              |
| workplaceId            | UUID   | 勤務先ID（外部キー）                                                                            |
| startDate              | date   | ルール適用開始日                                                                                |
| endDate                | date?  | 内部用の排他終了日。UI では前日を「適用終了日（この日まで）」として表示し、NULLの場合は現在有効 |
| baseHourlyWage         | number | 基本時給（円、小数2位まで。NORMAL/LESSON型用）                                                  |
| holidayAllowanceHourly | number | 休日手当（円/時の加算手当。デフォルト0）                                                        |
| nightPremiumRate       | number | 深夜割増率（例：0.25 = 25%）                                                                    |
| dailyOvertimeThreshold | number | 1日の所定時間（超過分が残業対象）                                                               |
| overtimePremiumRate    | number | 残業割増率（将来拡張。例：0.25 = 25%）                                                          |
| holidayType            | enum   | 休日判定タイプ                                                                                  |

**制約条件**

- 適用期間の重複は保存可能だが、重複候補がある場合は API warning で通知する
- endDate は NULLか startDate より後
- baseHourlyWage > 0
- nightPremiumRate ≥ 0
- overtimePremiumRate ≥ 0
- dailyOvertimeThreshold > 0（時間、実数可）

**holidayType の説明**

- **NONE**: 休日判定なし（毎日同じ時給）
- **WEEKEND**: 土日を休日扱い
- **HOLIDAY**: 指定の祝日のみ休日扱い（将来拡張）
- **WEEKEND_HOLIDAY**: 土日と祝日を休日扱い

**使用例**

勤務先「コンビニA」:

- Rule 1: 2026-01-01 ～ 2026-03-31、baseHourlyWage=1100、nightPremiumRate=0.25
- Rule 2: 2026-04-01 ～ NULL、baseHourlyWage=1150、nightPremiumRate=0.25

勤務先「塾B」（CRAM_SCHOOL）:

- Rule 1: 2026-01-01 ～ 2026-03-31、baseHourlyWage=1100、nightPremiumRate=0.0
- Rule 2: 2026-04-01 ～ NULL、baseHourlyWage=1200、nightPremiumRate=0.0

## 3.3.1 ActualPayroll

実給与実績（勤務先ごとの支給月実績）

**説明**: 給与明細をもとに、勤務先ごとの支給月実績を保持する。シフト由来の概算給与は残しつつ、表示上は実績値を優先する。

| 属性             | 型       | 説明                                             |
| ---------------- | -------- | ------------------------------------------------ |
| id               | UUID     | 実給与レコードの一意識別子                       |
| workplaceId      | UUID     | 対象勤務先                                       |
| paymentMonth     | date     | 支給月（`YYYY-MM-01` として保持）                |
| taxableAmount    | decimal  | 課税対象額。給与・賞与など年収の壁判定対象を含む |
| nonTaxableAmount | decimal  | 非課税対象額。交通費など年収の壁判定対象外を含む |
| note             | string?  | 補足メモ。任意                                   |
| createdAt        | datetime | 登録日時                                         |
| updatedAt        | datetime | 更新日時                                         |

**制約条件**

- 単位は `workplaceId + paymentMonth` の一意制約とする。
- `taxableAmount`, `nonTaxableAmount` は 0 以上。
- 控除・手取り額は保持しない。
- 実績未登録はレコードなしで表現する。

## 3.4 TimetableSet / Timetable

塾の時間割（CRAM_SCHOOL タイプの勤務先のみ使用）

**説明**: 塾の授業コマごとの開始・終了時刻を、勤務先ごとの `時間割セット` として管理する。シフト登録（LESSON型）時は `時間割セット + 開始コマ + 終了コマ` を選択し、`startTime/endTime` を自動計算する。

**用途**：

- LESSON型シフト時：「通常期」「夏期講習」などの時間割セットと「5限～7限」のようなコマ範囲を選択すると、該当コマの時刻を自動取得
- NORMAL型の場合も塾に登録可能（手入力、会議や事務作業など授業以外の業務を記録時に使用）

**TimetableSet 属性**

| 属性        | 型       | 説明                                       |
| ----------- | -------- | ------------------------------------------ |
| id          | UUID     | 時間割セットの一意識別子                   |
| workplaceId | UUID     | 勤務先ID（CRAM_SCHOOL のみ、外部キー）     |
| name        | string   | 時間割セット名（例: `通常期`, `夏期講習`） |
| sortOrder   | int      | 一覧表示順。小さいほど先に表示される       |
| createdAt   | datetime | 作成日時                                   |
| updatedAt   | datetime | 更新日時                                   |

**Timetable 属性**

| 属性           | 型   | 説明                     |
| -------------- | ---- | ------------------------ |
| id             | UUID | コマ行の一意識別子       |
| timetableSetId | UUID | 所属する時間割セットID   |
| period         | int  | コマ番号（1, 2, 3, ...） |
| startTime      | time | コマの開始時刻（HH:MM）  |
| endTime        | time | コマの終了時刻（HH:MM）  |

**制約条件**

- workplaceId は `CRAM_SCHOOL`
- `(workplaceId, name)` は一意
- `(timetableSetId, period)` は一意
- period は 1〜30 の整数。既存の範囲外データは表示できるが、次回保存時に範囲内へ修正が必要
- startTime と endTime は同時刻不可。新規作成・更新の API と UI の双方で、endTime は startTime より後でなければならず、同時刻および翌日跨ぎは許可しない
- 既存 DB に保存済みの翌日跨ぎ Timetable は、後方互換の read/resolver で LESSON の時刻計算に利用される場合がある。新規作成・更新の保存契約では翌日跨ぎを許可しない

**使用例**

塾「英語塾」の時間割:

時間割セット `通常期`:

- Period 1: 16:30 ～ 17:30
- Period 2: 17:40 ～ 18:40
- Period 3: 18:50 ～ 19:50

時間割セット `夏期講習`:

- Period 1: 15:00 ～ 16:20
- Period 2: 16:30 ～ 17:50
- Period 3: 18:00 ～ 19:20

## 3.5 Shift

シフト（実際の勤務）

**説明**: ユーザーが登録する実際の勤務シフト。勤務先ごと・日ごとに複数登録可能。Google Calendar と同期。

**LESSON型の特徴**：

- ユーザーは「5限～7限」のようにコマ範囲を選択
- Timetableから該当コマの時刻を自動計算 → `startTime/endTime` に格納
- ShiftLessonRange で「どのコマ範囲か」を記録
- Google Calendar には自動計算された時刻で登録される

**NORMAL型（塾での会議・事務作業など授業以外の業務）の特徴**

- ユーザーが時刻を手入力
- 時給で給与計算される（PayrollRule の baseHourlyWage を使用）

| 属性                    | 型       | 説明                                             |
| ----------------------- | -------- | ------------------------------------------------ |
| id                      | UUID     | シフトの一意識別子                               |
| workplaceId             | UUID     | 勤務先ID（外部キー）                             |
| date                    | date     | シフトの勤務開始日                               |
| startTime               | time     | シフト開始時刻（HH:MM）                          |
| endTime                 | time     | シフト終了時刻（HH:MM）                          |
| breakMinutes            | int      | 休憩時間（分単位、デフォルト0）                  |
| transportationAllowance | int      | シフト単位の交通費（整数円、未入力は0）          |
| shiftType               | enum     | シフトのタイプ（NORMAL, LESSON）                 |
| comment                 | string?  | 表示・Google Calendar イベント名用の任意コメント |
| isConfirmed             | boolean  | シフト確定フラグ（デフォルト false）             |
| googleEventId           | string?  | Google Calendar のイベントID（同期用）           |
| createdAt               | datetime | シフト登録日時                                   |

**制約条件**

- 同一勤務先の時間帯重複は、日跨ぎ解釈後の開始日時・終了日時で判定する（バリデーション段階で警告）
- startTime と endTime は同時刻不可
- NORMAL型では endTime < startTime の場合、翌日終了のシフトとして扱う。LESSON型の時刻は Timetable から導出し、新規・更新時の Timetable 保存契約では翌日跨ぎを許可しない（既存の翌日跨ぎ Timetable は read/resolver 互換で計算される場合がある）
- breakMinutes は整数で 0 ～ 240 分とし、日跨ぎ補正後の総勤務時間より短くする（実勤務時間 0 は保存しない）
- comment は任意。未入力・空文字・空白のみは NULL として保存
- comment は最大100文字、改行不可
- transportationAllowance は0円以上の整数円。未入力は0円とし、負数・小数は保存しない
- shiftType = LESSON の場合、ShiftLessonRange が1件以上存在
- shiftType = LESSON 以外の場合、ShiftLessonRange は存在しない

**勤務先表示名・イベント名**

- comment が NULL の場合: `勤務先名`
- comment がある場合: `勤務先名 (コメント)`
- 従来の塾タイプ NORMAL シフトに対する自動の ` (事務)` 表記は廃止する。事務として表示したい場合は comment に `事務` を入力する。

**shiftType の説明**

- **NORMAL**: 通常勤務（手入力。勤務先がCRAM_SCHOOLの場合は会議や事務作業など授業以外の業務も含む。時給で給与計算）
- **LESSON**: 塾の授業（CRAM_SCHOOL のみ。ShiftLessonRange で「何コマ目から何コマ目まで」を定義。時刻は Timetable から自動計算）

**使用例**

- 2026-03-20、コンビニA、10:00 ～ 18:00、NORMAL、breakMinutes=60
- 2026-03-21、塾B、16:30 ～ 19:50、LESSON（Period 1～3）、breakMinutes=0

---

## 3.6 ShiftLessonRange

塾のコマ範囲（Shift.shiftType = LESSON の場合のみ）

**説明**: LESSON タイプのシフトが どのコマから どのコマまでをカバーするかを記録。Timetable のコマに対応する。複数コマの授業を1シフトで記録可能。

**注記**：`startPeriod ≤ endPeriod` の同じ `timetableSetId` に属するコマ範囲を指す。

| 属性           | 型   | 説明                                         |
| -------------- | ---- | -------------------------------------------- |
| id             | UUID | レコードの一意識別子                         |
| shiftId        | UUID | シフトID（外部キー）                         |
| timetableSetId | UUID | 参照する時間割セットID                       |
| startPeriod    | int  | 開始コマ番号                                 |
| endPeriod      | int  | 終了コマ番号（startPeriodと同じ場合は1コマ） |

**制約条件**

- shiftId の Shift.shiftType = LESSON
- timetableSetId は Shift の勤務先に紐づく TimetableSet を参照する
- startPeriod ≤ endPeriod
- startPeriod, endPeriod は 1〜30 の整数。既存の範囲外データは表示できるが、次回保存時に範囲内へ修正が必要
- startPeriod, endPeriod は `timetableSetId` で指定した Timetable の period に存在する
- 1シフトあたり1件（複数コマの授業を1つのシフトで表現）

**使用例**

- Shift（2026-03-21、塾B、16:30 ～ 19:50、LESSON）
  → ShiftLessonRange: startPeriod=1, endPeriod=3

# 4. 主要ユースケース

---

## UC-001: シフト登録

**目的**: 新しいシフトをDB に登録し、Google Calendar に同期する。

**前提条件**

- ユーザーがログイン状態
- 勤務先が最低1件登録済み
- （LESSON の場合）塾の時間割が設定済み

**フロー**

1. ユーザーがカレンダーから日付をクリック
2. シフト入力フォーム表示（勤務先、シフトタイプなど）
3. ユーザーが情報を入力
   - **NORMAL型の場合**：開始時刻・終了時刻を手入力
   - **LESSON型の場合**：コマ範囲（e.g. Period 1～3）を選択 → サーバー側で Timetable から時刻を自動計算
4. クライアント側でバリデーション（必須項目、時刻の妥当性など）
5. NORMAL型で終了時刻 < 開始時刻の場合、翌日終了として扱う確認ダイアログを表示
6. バリデーション OK → POST /api/shifts（Shift + ShiftLessonRange を作成）
7. サーバー側で：
   - LESSON型の場合、Timetable から `startTime/endTime` を自動計算
   - Shift を INSERT → ShiftLessonRange を INSERT
8. DB 保存成功 → POST /api/calendar-sync にイベント作成を依頼（自動計算した時刻を使用）
9. Google Calendar API でイベント作成 → googleEventId を Shift に UPDATE
10. 成功レスポンス → 前画面へ戻る + 成功メッセージ表示

**エラーハンドリング**

- バリデーションエラー → UI でユーザーに指摘し、修正を促す
- Google Calendar API エラー → DB には保存済み、スタッシュして後で再同期（将来）

---

## UC-002: シフト編集

**目的**: 既存シフトを編集し、Google Calendar に反映する。

**前提条件**

- ユーザーがログイン状態
- 編集対象のシフトが存在

**フロー**

1. ユーザーがカレンダーまたはシフト一覧からシフトを選択
2. シフト詳細/編集フォーム表示（既存値をプリセット）
3. ユーザーが値を変更 → 「更新」ボタンをクリック
4. クライアント側でバリデーション
5. 更新後に終了時刻 < 開始時刻となる場合、翌日終了として扱う確認ダイアログを表示
6. バリデーション OK → PUT /api/shifts/{id}（Shift + ShiftLessonRange を更新）
7. サーバー側で Shift を UPDATE + ShiftLessonRange を DELETE/INSERT
8. DB 更新成功 → PUT /api/calendar-sync/{googleEventId} でイベント更新
9. Google Calendar API でイベント更新
10. 成功レスポンス → 前画面へ戻る + 成功メッセージ表示

**エラーハンドリング**

- 同じシフト内での時間帯重複チェック（警告のみ）
- Google Calendar API エラー → DB は更新済み

---

## UC-003: シフト削除

**目的**: シフトを削除し、Google Calendar から削除する。

**前提条件**

- ユーザーがログイン状態
- 削除対象のシフトが存在

**フロー**

1. ユーザーがシフトの「削除」ボタンをクリック
2. 対象シフトを一覧・カレンダーから楽観的に除去し、「削除しました」と4秒間の「元に戻す」アクション付きトーストを表示
3. 期限内に「元に戻す」を選択した場合、削除 Server Action を呼ばずに表示を復元
4. 期限経過後、削除 Server Action をバックグラウンドで呼び出す（成功時の追加トーストは表示しない）
5. サーバー側で ShiftLessonRange を DELETE → Shift を hard delete
6. DB 削除成功後、DELETE /api/calendar-sync や Google Calendar API でイベント削除（googleEventId で識別）
7. 削除時に進行中の月次取得をキャンセルし、削除処理後は月次シフトを即時再フェッチしない。楽観的に除去したシフトが古い取得結果でカレンダーへ再表示されることを防ぐ。

**エラーハンドリング**

- 削除 Server Action 失敗 → 楽観的に除去したシフトを表示へ復元し、エラー通知を表示
- Google Calendar API エラー → DB は既に削除済み（スタッシュして後で手動対応）

# 7. Google Calendar同期

## 7.1 基本ルール

| 操作     | 処理                                        | 詳細                                                   |
| -------- | ------------------------------------------- | ------------------------------------------------------ |
| 作成     | イベント作成                                | DB保存後、その日のイベント ID を shifts テーブルに記録 |
| 編集     | イベント更新                                | 既存の googleEventId でイベント再作成または更新        |
| 削除     | イベント削除                                | googleEventId をキーに削除                             |
| 同期失敗 | DB には保存済み、同期ステータスをスタッシュ | 将来の「同期再試行」機能で対応予定                     |

## 7.2 Google Calendar 側の編集について

Google Calendar 側で シフトのイベントを編集しても、アプリには反映しない。データの正はアプリケーション DB。

**理由**: 複数勤務先・複数デバイスでのシフト管理の一貫性を保つため、DB を単一の真実の根拠地（SSOT）とする。

## 7.3 イベント属性のマッピング

| Shift 属性               | Google Calendar イベント属性             | 説明                                                                      |
| ------------------------ | ---------------------------------------- | ------------------------------------------------------------------------- |
| date, startTime, endTime | start, end                               | ISO 8601 形式で保存。endTime < startTime の場合、end は翌日日時として保存 |
| workplaceId              | カスタムプロパティ（extendedProperties） | JSONで勤務先ID等を保存（検索用）                                          |
| workplace.name, comment  | title                                    | comment がある場合は `勤務先名 (コメント)`、ない場合は `勤務先名` を使用  |
| color（勤務先）          | （指定しない）                           | colorId は送信せず、Google Calendar 側の既定色を使用                      |

# 8. 給与計算仕様

## 8.1 対象・非対象

**対象**

- **NORMAL型**: 基本給、休日手当（時間あたり加算）、深夜割増
- **LESSON型**: 基本給、休日手当（時間あたり加算）、深夜割増。時刻は時間割から自動解決し、コマ数は表示用に保持する

**非対象（MVP では未対応）**

- 控除（税金、社会保険など）
- 週単位での残業計算
- 月60時間を超える残業（法定外残業）
- 通勤手当・その他手当

---

## 8.2 計算の基本フロー

1. 対象期間内のすべての Shift を取得
2. Shift ごとに該当する PayrollRule を時系列で確定
3. Shift ごとに以下を計算：
   - **NORMAL型**: 実勤務時間、深夜帯勤務時間、休日時間を分類し、給与を計算
   - **LESSON型**: 時間割から解決した `startTime/endTime` を使って NORMAL型と同じ時給計算を行い、あわせてコマ数（`endPeriod - startPeriod + 1`）を記録する
4. 期間合計を集計

---

## 8.3 計算式

### 8.3.1 勤務時間の分類

**実勤務時間（H_total）**

```
H_total = (endTime - startTime - breakMinutes) / 60 [時間]
```

- endTime < startTime の場合、endTime は翌日の時刻として計算する。
- 休憩は勤務時間の内訳位置を保持しない。現行の給与計算では `H_night = min(H_total, 休憩控除前の深夜帯重複時間)`、`H_base = max(0, H_total - H_night)` とする。深夜帯内外への正確な休憩配分には、休憩位置を保持するスキーマ拡張が必要であり、本仕様の対象外とする。

**深夜帯勤務時間（H_night）**

- `min(H_total, 22:00 ～ 05:00 の休憩控除前の時間帯重複時間)`（固定）
- 例：22:00 ～ 05:00 の場合
  - 22:00 ～ 24:00（2時間）と 00:00 ～ 05:00（5時間）の合計
  - 翌日にまたがる場合は合算

**基本時間（H_base）**

```
H_base = max(0, H_total - H_night)
```

**休日時間（H_holiday）**

```
H_holiday = 休日判定に合致する日の場合 H_total、それ以外は 0
```

### 8.3.2 給与計算

**NORMAL型のシフト（1シフト分）**

基本前提

- 休日判定は `holidayType` に基づく
- 深夜割増率は `nightPremiumRate`（0以上）
- 休日手当は `holidayAllowanceHourly`（円/時、0以上）

```
基本支給 = H_base × baseHourlyWage

深夜支給 = H_night × baseHourlyWage × (1 + nightPremiumRate)

休日支給 = H_holiday × holidayAllowanceHourly

シフト合計給 = round(基本支給) + round(深夜支給) + round(休日支給)
```

※ `overtimePremiumRate` は将来拡張用に保持するが、現時点のV2計算では使用しない。

**LESSON型のシフト（1シフト分）**

```
コマ数 = endPeriod - startPeriod + 1

シフト合計給 = NORMAL型と同じ式で計算
```

**補足**

- LESSON型も給与計算は `baseHourlyWage` ベースで行う
- 休日時間は基本時間・深夜時間とは独立に扱う（休日夜勤では深夜支給と休日支給の両方が発生）
- 詳細なルールは実装時に業務ロジックで定義

## 8.4 具体例

### 例1：通常勤務（NORMAL シフト）

**条件**

- 勤務先：コンビニA（GENERAL）
- 日付：2026-03-20（金、平日）
- 時間：10:00 ～ 18:00
- 休憩：60分
- PayrollRule：baseHourlyWage=1100, nightPremiumRate=0.25, holidayAllowanceHourly=0

**計算**

```
H_total = (18:00 - 10:00 - 60) / 60 = 7 時間
H_night = 0（深夜帯なし）
H_base = 7 時間
H_holiday = 0 時間

基本支給 = 7 × 1100 = 7,700 円
深夜支給 = 0 円
休日支給 = 0 円

給与 = 7,700 円
```

### 例2：夜勤シフト（NORMAL シフト、深夜帯含む）

**条件**

- 勤務先：別のコンビニ
- 日付：2026-03-21（土、休日判定で WEEKEND）
- 時間：22:00 ～ 翌05:00
- 休憩：30分
- PayrollRule：baseHourlyWage=1100, holidayAllowanceHourly=100, nightPremiumRate=0.25, holidayType=WEEKEND

**計算**

```
H_total = (05:00 (次日) - 22:00 - 30) / 60 = 6.5 時間
H_night = 6.5 時間（全て深夜帯）
H_base = 0 時間
H_holiday = 6.5 時間

基本支給 = 0 × 1100 = 0 円
深夜支給 = 6.5 × 1100 × 1.25 = 8,937.5 円 → 8,938 円
休日支給 = 6.5 × 100 = 650 円

給与 = 8,938 + 650 = 9,588 円
```

### 例3：塾の授業（LESSON シフト）

**条件**

- 勤務先：塾B（CRAM_SCHOOL）
- 日付：2026-03-22（日）
- シフトタイプ：LESSON（時間割セット `通常期` の Period 1～3）
- Timetable（時間割セット `通常期`）：
  - Period 1: 16:30 ～ 17:30
  - Period 2: 17:40 ～ 18:40
  - Period 3: 18:50 ～ 19:50
- 自動計算：startTime=16:30、endTime=19:50、コマ数=3
- PayrollRule：baseHourlyWage=1100, holidayAllowanceHourly=1200, nightPremiumRate=1.0

**計算**

```
H_total = (19:50 - 16:30) = 3時間20分 = 3.33時間
コマ数 = 3 - 1 + 1 = 3 コマ

給与 = round(3.33 × 1100) = 3,667 円
```

### SCR_003: カレンダー

**目的**: 月間シフト一覧を視覚的に表示し、シフト登録・編集・削除のエントリーポイントを提供する。

**ヘッダー機能**

**カレンダー表示**

- **形式**: 月間カレンダー（日曜始まり）
- **日付セル**: 日付の数字を表示
- **空きセル**: 前月・次月の日付は薄く表示（クリック不可）

**シフト表示（新規仕様）**

​日付セルの下部に、その日に登録されているシフト数に応じて色付き丸を表示：

- **1件のシフト**: そのシフトの勤務先の色の丸（直径約6～8px）を1つ表示
- **複数件**: 各シフトの勤務先色に対応した丸を**横並び**に表示（最大5～6件、超過は「+N」テキスト）
- **色の由来**: 各丸の色は `Workplace.color` フィールドから取得
- **配置**: 日付の数字より下、セルの中央下部に配置

**例**

```
┌─────────────┐
│      5      │   ← 日付数字
│             │
│    ● ●     │   ← シフトが2件（勤務先Aとワークプレイス Bの色の丸）
└─────────────┘

┌─────────────┐
│      12     │
│             │
│  ● ● ● +2  │   ← シフトが5件以上（色の丸3つ + "+2" テキスト）
└─────────────┘
```

**インタラクション**

| アクション             | 動作                                                                                            |
| ---------------------- | ----------------------------------------------------------------------------------------------- |
| **日付クリック**       | シフト有無にかかわらず、その日のシフト一覧モーダルを表示                                        |
| **シフト表示クリック** | その日のシフト一覧モーダルを表示 → シフト選択で編集/削除                                        |
| **マウスホバー**       | 丸上に勤務先表示名をツールチップ表示（2秒後に表示）。comment がある場合は `勤務先名 (コメント)` |

- シフトがない日をホバーまたはキーボードフォーカスすると、「確認・追加」の補助表示で追加可能なことを示す。通常時のセル内情報量は増やさない。
- シフトがない日のモーダルには「この日に追加」ボタンを表示し、選択日を初期値として SCR_004 へ遷移する。
- ダッシュボードヘッダーの「新規シフト登録」は、カレンダーで選択中の日付を初期日とする。選択日が表示月外の場合は、表示月内の当日と同じ日付（存在しない場合は月末日）を初期日とする。

**シフト一覧モーダル**（日付クリック時の選択肢）

- **表示内容**: その日のシフト一覧（時刻、勤務先表示名、給与予想含む）。comment がある場合、勤務先表示名は `勤務先名 (コメント)`
- **アクション**:
  - シフト行クリック → SCR_005 (シフト編集) へ遷移
  - 「新規追加」ボタン → SCR_004 (シフト入力) へ遷移

**ローディング表示**

- 初回表示時は全体スピナーを表示してよい。
- 月切替や再取得時は、既存の LoadingOverlay・`aria-busy=true`・操作制御を維持する。画面内の `最新データを更新中...` 通知は表示せず、右下に非操作型スピナーと `更新中` をフローティング表示する。

### SCR_004: シフト入力

**目的**: 新規シフトをDB に登録し、Google Calendar に同期する。

**フォーム定義**

| フィールド   | 型     | 必須 | 仕様                                                                                           |
| ------------ | ------ | ---- | ---------------------------------------------------------------------------------------------- |
| 勤務先       | SELECT | ○    | 登録済み勤務先から選択; デフォルト = 前回選択した勤務先                                        |
| 日付         | DATE   | ○    | カレンダーピッカー or 手入力; デフォルト = クリック日                                          |
| シフトタイプ | RADIO  | ○    | NORMAL / LESSON; デフォルト = NORMAL                                                           |
| 開始時刻     | TIME   | ◆    | NORMAL型のみ表示; HH:MM 形式; バリデーション: 00:00 ～ 23:59                                   |
| 終了時刻     | TIME   | ◆    | NORMAL型のみ表示; HH:MM 形式; 開始時刻と同時刻は不可。開始時刻より早い場合は翌日終了として扱う |
| 休憩時間     | NUMBER | ○    | 分単位; デフォルト = 0; 整数の 0 ～ 240 かつ日跨ぎ補正後の総勤務時間未満                       |
| 交通費       | NUMBER | ー   | シフト単位の円額; 未入力 = 0; 0以上の整数（負数・小数不可）                                    |
| 時間割セット | SELECT | ◆    | LESSON型のみ表示; 勤務先に紐づく時間割セットから選択                                           |

| 終了コマ     | SELECT | ◆    | LESSON型のみ表示; `開始コマ` 以上で、選択した時間割セットに存在するコマ番号から選択            |
| コメント     | TEXT   | ー   | 任意; 最大100文字; 改行不可; 空文字・空白のみは NULL として保存                                |

**説明**

- **◆ 条件付き必須**: シフトタイプに応じて表示・必須が変わる
  - NORMAL型: `開始時刻`、`終了時刻` は必須。`時間割セット`、`開始コマ`、`終了コマ` は非表示
  - LESSON型: `時間割セット`、`開始コマ`、`終了コマ` は必須。`開始時刻`、`終了時刻` は非表示（Timetableから自動計算）
- コメント入力欄の下に Google Calendar のイベント名登録イメージをリアルタイム表示する。
  - comment 入力あり: `イベント名プレビュー「勤務先名 (コメント)」`
  - comment 未入力: `イベント名プレビュー「勤務先名」`
  - 勤務先未選択の場合は、プレビューを非表示にするか `勤務先を選択するとイベント名を確認できます` と表示する。
- 交通費入力欄は新規・編集のシフトフォームに表示し、支給額プレビューでは給与と分けて非課税額として扱う。

**バリデーション**

1. **必須チェック**: 条件付き必須項目を確認
2. **時刻バリデーション**:
   - NORMAL型: 開始時刻と終了時刻は同時刻不可
   - NORMAL型で終了時刻 < 開始時刻の場合、翌日終了として扱い、保存前に確認ダイアログを表示する
   - （警告）日跨ぎ解釈後の時間帯が既存シフトと重複している場合の警告
3. **コマ範囲**: LESSON型選択時、有効なコマが存在するか確認
4. **休憩時間**: NORMAL の入力値および LESSON の時間割から導出した値を、整数の 0 ～ 240 分かつ日跨ぎ補正後の総勤務時間未満として確認する
5. **コメント**: 最大100文字、改行不可。空文字・空白のみは NULL

**日跨ぎ確認ダイアログ**

- 対象: NORMAL型で終了時刻 < 開始時刻の場合
- 表示タイミング: 登録送信前
- 表示内容: 開始日時、終了日時、翌日終了として登録する旨
- アクション: `キャンセル` / `翌日終了として保存`

**SCR_005: シフト編集時の差分仕様**

- シフト編集フォームは SCR_004 と同じ時刻解釈を使用する。
- 編集後に終了時刻 < 開始時刻となる場合、保存前に日跨ぎ確認ダイアログを表示する。
- 既存シフトがすでに日跨ぎで、開始時刻・終了時刻を変更していない場合は確認を省略する。

**エラーメッセージ**

| エラーコード | メッセージ                                 |
| ------------ | ------------------------------------------ |
| ERR_001      | 〇〇は必須項目です                         |
| ERR_002      | 開始時刻と終了時刻は同じ時刻にできません   |
| ERR_003      | この日付にはすでにシフトが登録されています |
| ERR_004      | 塾の授業は時間割が登録されていません       |

### SCR_007: 給与集計

**目的**: 選択した年の給与サマリーを月次・勤務先別の年次表で表示する。

### SCR_015: シフト確定

**目的**: 本日までの未確定シフトを確認・修正し、確定処理を行う。未確定シフトをカードリスト形式で表示（時間変更可能）する。

**画面構成**

**Part 1: 未確定シフトリスト（上部）**

**リスト条件**

- 日付が本日以前（today 以前）
- `isConfirmed = false`

**リスト順序**

- `date ASC`（古い日付から新しい日付へ）

**リストが空の場合**

- 「未確定シフトはありません」メッセージを表示

**カード表示**

各未確定シフトを以下の形式でカード表示。複数カードが存在する場合はスクロール可能な領域に縦並びで表示：

| 要素       | 内容                                                       |
| ---------- | ---------------------------------------------------------- |
| 日付       | 「2026年3月5日（木）」など                                 |
| 勤務先名   | 勤務先の表示名。comment がある場合は `勤務先名 (コメント)` |
| 開始時刻   | **編集可能な入力フィールド** (TIME フォーマット)           |
| 終了時刻   | **編集可能な入力フィールド** (TIME フォーマット)           |
| 休憩時間   | **編集可能な入力フィールド** (数値、分単位)                |
| 確定ボタン | シフト確定処理トリガー                                     |
| 削除ボタン | シフト削除処理トリガー（確認ダイアログは表示しない）       |

**インタラクション**

| アクション                 | 動作                                                                                                                                                                                               |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **時刻/休憩時間編集**      | 入力値がリアルタイムに更新される。確定時に新値でDB更新される                                                                                                                                       |
| **確定ボタンクリック**     | 日跨ぎ確認が必要な場合は確認ダイアログ表示 → シフトの `isConfirmed` を `true` に更新 → DB反映 → カード削除                                                                                         |
| **削除ボタンクリック**     | カードを楽観的に除去し、「削除しました」と4秒間の「元に戻す」トーストを表示。期限経過後は hard delete をバックグラウンドで実行し、成功時は追加通知を表示しない。失敗時はカードを復元してエラー通知 |
| **編集値のバリデーション** | 開始時刻と終了時刻が同時刻でないこと、休憩時間が整数の0～240分かつ日跨ぎ補正後の総勤務時間未満であることを確認                                                                                     |

**ローディング表示**

- 初回表示は SSR で取得した未確定シフト一覧を用いる。画面を開くたび未確定一覧の有無・内容を背景再取得し、右下の非操作型「更新中」フローティング表示を出す。再取得中も画面全体をブロックせず、他のカード操作を継続できる。
- 確定後は対象カードを即時除去し、関連キャッシュを stale 化する。利用者の手動「更新」操作による再取得も引き続き可能とする。

**日跨ぎ確認ダイアログ**

- 対象: 確定時点で終了時刻 < 開始時刻となる未確定シフト
- 表示タイミング: 確定 API 送信前
- 表示内容: 開始日時、終了日時、翌日終了として確定する旨
- アクション: `キャンセル` / `翌日終了として確定`

**バリデーション（Part 1 の編集値）**

1. **時刻バリデーション**: 開始時刻と終了時刻が同時刻でないことを確認。終了時刻 < 開始時刻の場合は翌日終了として扱う

## 11.1 Google Calendar 同期フロー

| シフト操作 | 同期アクション | イベント属性                                                           | 注記                 |
| ---------- | -------------- | ---------------------------------------------------------------------- | -------------------- |
| **作成**   | イベント作成   | title: comment ありは `勤務先名 (コメント)`、comment なしは `勤務先名` | googleEventId を保存 |
| **編集**   | イベント更新   | 時間・タイトルを更新。comment 削除時は `勤務先名` のみに戻す           | googleEventId で識別 |
| **削除**   | イベント削除   | googleEventId にて削除                                                 | DB削除と同期         |

**同期失敗時の処理**

- DB には既に保存済み
- ユーザーに「Googleカレンダーとの同期に失敗しました」と表示
- 詳細ログはサーバー側に記録
- 将来「同期再試行」機能で手動対応

**遷移優先 + バックグラウンド同期方針（2026-06）**

- シフト作成/編集/削除/確定/一括登録は、DB更新完了時点でHTTPレスポンスを返し、Google同期は `after()` でバックグラウンド実行する。
- 更新系レスポンスは `sync` オブジェクトを返し、`status=pending` と `pending=true` で「同期実行中」を表す。
- クライアントは `sync.failure` がない限り遷移を継続し、`pending` の場合は非ブロッキング通知のみ表示する。
- 一括シフト作成とカレンダー初期化後の既存シフト同期は、同一 Node.js instance 内で共有する最大3件の同期 permit と最大100件の待機列を利用する。Google Calendar の事前検証と、イベント作成およびそのリトライを含む各シフト同期単位で permit を取得し、複数のバックグラウンド同期呼び出しをまたいでも同時実行数を3件以下にする。待機列の上限を超えたジョブは明示的に `FAILED` として終了し、再スケジュールしない。Google の retryable な応答に `Retry-After` がある場合は、既存の待機時間以上かつ最大30秒として尊重し、待機中も permit を保持する。permit と待機列はいずれも instance-local であり、Node.js instance 間では共有しない。

### 2. 用語定義

- 締日:
  - 各勤務先の給与計算期間を区切る日付。
  - 設定値は `1..31` または `月末締め`。

  - 実日付は対象月の日数に合わせて丸める（例: 31日指定で2月は末日）。
- 支給月:
  - 13章の集計基準となる、選択年内の各月（`YYYY-MM`）。
- 対象勤務期間:
  - 支給日の実日付から過去に遡って直近の締日を `endDate` とし、その1つ前の締日の翌日を `startDate` とする期間。
  - 期間は `startDate` と `endDate` の両端を含む。

#### 3.2 制約

- `締日設定 = DAY_OF_MONTH` のとき `締日` は必須。

### 5. アルゴリズム詳細

#### 5.1 日付丸め

- `day` 指定が対象月の末日を超える場合は末日に丸める。
  - 例: 31日指定 + 2026-02 => 2026-02-28

#### 5.2 締日列挙

- `DAY_OF_MONTH(d)`:
  - 各月の締日は `min(d, 月末日)`。
- `END_OF_MONTH`:
  - 各月の締日は月末日。

#### 5.3 対象勤務期間の導出

- `paymentDate` を基準に、`paymentDate` 以下で最大の締日を `periodEndDate` とする。
- `periodEndDate` より前で最大の締日を `previousClosingDate` とする。
- `periodStartDate = previousClosingDate + 1日`。

#### 5.4 例

- 例1: 締日=15日, 給料日=25日, 支給月=2026-04
  - `paymentDate = 2026-04-25`
  - `periodEndDate = 2026-04-15`
  - `periodStartDate = 2026-03-16`
  - 対象期間: `2026-03-16 〜 2026-04-15`

- 例2: 締日=月末, 給料日=20日, 支給月=2026-04
  - `paymentDate = 2026-04-20`
  - `periodEndDate = 2026-03-31`
  - `periodStartDate = 2026-03-01`
  - 対象期間: `2026-03-01 〜 2026-03-31`

### 5. 給与内訳・計算ロジックの表示定義

本章は「表示上の定義」。計算エンジン自体は既存ロジックを利用する。

#### 5.1 時間

- `勤務時間(H_total)` = `(endTime - startTime - breakMinutes) / 60`
- `基本勤務時間(H_base)` = `max(0, H_total - H_night)`（深夜時間とは重複しない）
- `休日勤務時間(H_holiday)`:
  - 休日判定が `true` のシフトでは `H_total`
  - 休日判定が `false` のシフトでは `0`
- `深夜勤務時間(H_night)` = 固定の22:00〜翌05:00との重複時間
- `残業時間(H_overtime)` = `max(0, H_total - dailyOvertimeThreshold)`
- 時間表示ルール:
  - テーブル表示は `h:mm` 形式（例: `7:30`）
  - 計算内部は従来どおり小数時間で扱う
  - `H_night` は `H_base` と重複しない。`H_holiday` とは独立して扱う。

#### 5.2 時給の選択

- 常に `baseHourlyWage` を基本単価として使用する。
- `holidayAllowanceHourly` は休日時間に対する独立した加算手当（円/時）として使用する。

#### 5.3 金額内訳（1シフト）

- `基本勤務金額` = `H_base × baseHourlyWage`
- `休日勤務金額` = `H_holiday × holidayAllowanceHourly`（`holidayAllowanceHourly` による独立加算）
- `深夜勤務金額` = `H_night × baseHourlyWage × (1 + nightPremiumRate)`
- 表示上の深夜勤務式は「深夜時間 × 深夜時給（割増込）」とし、深夜時給は `baseHourlyWage × (1 + nightPremiumRate)` で求める。
- `残業金額` = `0`（`H_overtime` は参考表示のみ。総額に加算しない）
- `シフト合計` = `round(基本勤務金額) + round(休日勤務金額) + round(深夜勤務金額)`

注記:

- `overtimePremiumRate` は将来拡張用に保持するが、V2では計算に使用しない。
- LESSON 型シフトも現行実装では時給計算で集計する。

#### 5.4 月合計・年合計

- 月合計 = 対象シフトの `シフト合計` 総和
- 年合計 = 対象年1月〜12月の月合計総和

#### 5.5 金額表示ルール

- 金額の単位表記は `¥` を使用する。
- 表記例: `¥44,720`

# 15. シフト登録時の翌月支給額プレビュー仕様（2026-05-10 統合）

本章は、シフト登録時に未保存シフトを反映した概算支給額を即時確認するための仕様である。

詳細な実装計画は `docs/archive/feature-plans/2026-05-10_shift-payroll-preview-plan.md` を参照する。

対象:

- SCR_004（シフト入力）
- SCR_014（シフト一括登録）

非対象:

- SCR_015（シフト確定）
- Google Calendar 側予定の取り込み・逆同期

---

### 1. 目的

- シフト登録前に、入力中の未保存シフトを含めた支給月別の概算支給額を確認できるようにする。
- ユーザーが支給見込を見ながらシフト入力・一括入力を調整できるようにする。
- 一括登録で複数支給月に渡る場合でも、支給月ごとの影響額を把握できるようにする。

---

### 2. 表示単位

表示単位は「支給月」とする。

- 「翌月支給額」は単純な翌カレンダー月ではなく、13章の給与締日・給料日仕様に基づく `支給月` として扱う。
- 勤務先ごとの締日・給料日により、同じ勤務日でも属する支給月が異なる場合がある。
- 入力中シフトが複数支給月に分かれる場合、該当する全支給月を昇順で表示する。

例:

- 月末締め / 25日払いの勤務先では、`2026-06-10` のシフトは `2026-07` 支給に含まれる。
- 15日締め / 25日払いの勤務先では、`2026-06-10` のシフトは `2026-06` 支給、`2026-06-20` のシフトは `2026-07` 支給に含まれる。

---

### 3. 表示内容

支給月ごとに以下を表示する。

| 項目           | 内容                                             |
| -------------- | ------------------------------------------------ |
| 支給月         | `YYYY年M月支給`                                  |
| 現在の支給見込 | DB 保存済みシフトのみで計算した支給額            |
| 追加予定額     | 入力中の未保存シフトのみで計算した支給額         |
| 登録後見込     | `現在の支給見込 + 追加予定額`                    |
| 対象シフト数   | その支給月へ反映される未保存シフト件数           |
| 計算状態       | 未入力、不足情報あり、給与ルール不足、計算済み等 |

表示ルール:

- 金額は `¥12,345` 形式で表示する。
- 追加予定額は `+¥3,200` のように差分であることが分かる形式にする。
- `登録後見込` を最も強調する。
- 各段階（現在・追加予定・登録後見込）に「課税合計」と「非課税込み総支給額」を表示する。課税合計は給与、非課税込み総支給額は給与と交通費の合計とする。
- 計算中表示は入力操作をブロックしない。

---

### 4. 金額計算

各支給月のプレビューは以下で計算する。

```text
登録後見込 = 現在の支給見込 + 入力中シフトの追加予定額
課税合計 = 給与合計
非課税込み総支給額 = 課税合計 + 交通費合計
```

現在の支給見込:

- DB 保存済みシフトだけを対象にする。
- 13章の支給月基準で集計する。
- 未確定シフトも含める。
- Google Calendar 側の予定は含めない。

追加予定額:

- 入力中フォームの未保存シフトだけを対象にする。
- クライアント側で即時計算する。
- 給与計算式は8章および `docs/PAYROLL_CALCULATION_SPEC_V2_20260430.md` に従う。
- プレビュー専用の独自計算式は作らない。
- 給与を課税額、シフト単位の `transportationAllowance` を非課税額として集計する。
- LESSON型では、選択したコマ範囲の時間割から `startTime/endTime` と `breakMinutes` を算出する。
  - コマ間ギャップを `breakMinutes` として扱う。
  - 算出ロジックはシフト保存時（`/api/shifts`）と同一の共通関数を利用する。

---

### 5. 入力不備時の扱い

入力途中で計算できないシフトがあっても、プレビュー全体は破綻させない。

| 状態                   | 表示方針                                               |
| ---------------------- | ------------------------------------------------------ |
| 勤務先未選択           | `勤務先を選択すると支給額を確認できます`               |
| 日付未入力             | `日付を入力すると支給月を判定できます`                 |
| 時刻未入力             | `開始時刻と終了時刻を入力すると追加予定額を計算します` |
| 同時刻エラー           | フォームバリデーションを優先し、金額は表示しない       |
| 給与ルール不足         | `この日付に適用できる給与ルールがありません`           |
| 時間割不足             | `塾の時間割が登録されていません`                       |
| 一括登録の一部行が不備 | 有効行だけを合算し、未計算件数を補足表示する           |

一括登録で一部行に不備がある場合:

- 有効行の追加予定額は表示する。
- `未計算: N件` を表示する。
- 登録ボタン押下時の既存バリデーションは維持する。

- 給与ルール、給与サイクル、時間割はフォーム既存取得データを可能な限り再利用する。
- 一括登録では給与ルール・給与サイクル・時間割を `Map` 化し、入力行ごとの過剰な探索を避ける。

# 16. 実給与登録・実績優先表示仕様（2026-06-18）

対象:

- SCR_007（給与集計）
- SCR_016A / SCR_016B（給与詳細）
- SCR_017（実給与編集）
- `ActualPayroll` ドメイン

### 1. 目的

- 給与明細で確定した実際の支給額を、支給月単位で登録できるようにする。
- 年収の壁判定に使うため、`課税対象` と `非課税対象` を分けて保持する。
- 給与サマリーと給与詳細では、実績がある箇所は実績値を優先表示し、概算値は比較用に残す。

### 2. 登録単位と入力項目

- 登録単位は `勤務先 × 支給月` とする。
- 支給月は `YYYY-MM` で選択し、DB では月初日 `YYYY-MM-01` として保持する。
- 入力項目:
  - `課税対象額`
  - `非課税対象額`
  - `メモ`（任意）
- `実合計 = 課税対象額 + 非課税対象額`
- 両金額とも 0 以上。両方未入力かつメモ空の行は「未登録」として扱い、保存時はレコード削除対象とする。

### 3. 画面仕様

#### 3.1 SCR_017 実給与編集

- ルート: `/my/payroll/actual`
- サイドバーの `給与管理` 配下から遷移できる。
- 月選択で対象支給月を切り替える。
- 勤務先一覧には以下を表示する。
  - 勤務先名
  - 対象期間
  - 概算額
  - 課税対象額
  - 非課税対象額
  - 実合計
  - 差額（実合計 - 概算額）
  - メモ
- 保存は月単位一括保存とする。

#### 3.2 SCR_007 給与集計

- 総額カードは `実績支給額` を主表示とする。
- `実績支給額` は、勤務先ごとに `実給与があれば実績、なければ概算` を採用して合算する。
- `年内受取累計` と `年間受取見込` も、各月の `実績支給額` 合計を用いる。
- `概算給与` は比較用に併記する。

#### 3.3 SCR_016 給与詳細

- 月毎表示:
  - ヘッダーは `実績支給額` を最優先で表示する。
  - `実績支給額` カード内に `課税/非課税内訳（課税/非課税/合計）` を含め、`概算支給合計` を併記する。
  - 勤務先別には `表示金額` と `概算金額` を併記し、計算根拠の時間内訳・式は概算由来のまま維持する。
- 勤務先毎表示:
  - 年間主表示は、12か月分の `実績支給額` 合計を使う。
  - 月次表も `実績支給額` を優先し、`概算額` を比較列として残す。

### 4. API方針

- 新規 API:
  - `GET /api/payroll/actual?month=YYYY-MM`
  - `PUT /api/payroll/actual?month=YYYY-MM`
- `GET` は対象月の全勤務先について、概算値・対象期間・既存実給与値を返す。
- `PUT` は対象月の複数勤務先入力を受け取り、`workplaceId + paymentMonth` で upsert する。
- 既存 API の返却値には、表示用の `display` 概念を追加する。
  - `summary`: 月合計・累計・年合計に実績優先値を含める
  - `details/monthly`: 勤務先別・ヘッダー向けの実績優先値を含める
  - `details/workplace-yearly`: 月次行・年次カード向けの実績優先値を含める

### 5. 表示優先ルール

- 勤務先月次の主表示金額:
  - 実給与登録あり -> `実合計`
  - 実給与登録なし -> `概算額`
- 月合計・年合計・累計:
  - 各勤務先/各月の主表示金額を積み上げた値を正とする。
- 概算由来の勤務時間、深夜時間、休日時間、計算式は引き続き表示する。

### 6. 受け入れ条件

1. `/my/payroll/actual` から支給月別の実給与を登録できる。
2. 課税対象額と非課税対象額を分けて保存できる。
3. `給与サマリー` の主表示額と累計/年計が実績優先になる。
4. `給与詳細（月毎）` で実績値と概算値の両方を確認できる。
5. `給与詳細（勤務先毎）` の年合計は実績優先表示になる。
